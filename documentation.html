I. Prototype assumptions

  • Registration number format YYYY-DEPT-NNN (e.g. 2023-CS-045), batch (session) options 2022–2026 and sections A–D are placeholders; replace them with the department's real values.
  • Length limits: description 20–1000 characters; resolution note 10–500; location 3–100; optional messages up to 300.
  • Tracking reference format SVP- plus 6 characters. The generator uses Math.random() and is not secure.
  • Meeting dates and preferred dates cannot be in the past.
  • Rejected is shown as the final stage of the timeline in place of Resolved.
  • Dashboard and analytics figures are calculated from 18 dummy submissions instead of the brief's example totals (80), so the numbers stay consistent with the queue and change as you work.
  • Proposing a new meeting resets the student's response to “No Response”.
  • Analytics also shows monthly volume, staff workload and identified complaints by class timing, all derived from the same fields.
  • The queue includes a Type filter (Anonymous / Identified) in addition to search, category, status and date.
  • Scope change by project team: the Feedback & Suggestion path (original Module 3) has been removed, because complaints already cover the portal's purpose. The “Course workload” option has been removed from the Course category. A Class Timing field (Morning / Evening) has been added to identified complaints.
  • Meetings for identified complaints only: an anonymous student has not shared who they are, so the department responds through the resolution note instead. The Schedule Meeting button is disabled for anonymous complaints.
  • Suggestions without a feedback path: the Other category (Suggestion for improvement, Something not listed here) and Student Experience (Idea to improve student life) give non-complaint ideas a place. Both forms point this out under the category field.
  • Notification means in-portal updates on the student status page. Email, SMS and WhatsApp notifications remain out of scope.
  • Anonymous option descriptions: each predefined option has a short fixed description that appears on the form, success, status and admin pages. It explains the complaint without adding a free-text field, so the SRS rule of no typed text on anonymous complaints still holds.
  • No student login: students do not create accounts. Anonymous complaints stay account-free so they cannot be linked to a person or to each other; the tracking reference is the only link. Student accounts for identified complaints are a possible Version 2 feature.
  • Admin login, session, “Remember me” and data storage are simulated with localStorage. There is no real authentication, authorisation, database or security.

J. Presentation flow

  1. Introduction. “Our project is called Student Voice Portal. It is a centralized web-based platform that allows students to submit complaints, anonymously or with their details, and allows authorized department staff to manage, track and resolve those submissions.”
  2. Modules. Walk through the six modules: Foundation & Access Control; Complaint Submission (anonymous + identified); Review & Categorization; Resolution & Notification; Analytics & Reporting Dashboard; Meeting Scheduling (identified complaints only).
  3. Student demo. Home → Submit Complaint → Anonymous → pick Facilities / Classroom issue → submit (show validation first by submitting empty) → copy reference → Track → status (note: no meeting for anonymous). Then track SVP-8F4K29, an identified complaint, to show an admin response and a proposed meeting → Confirm Meeting.
  4. Admin demo. Admin Login (show invalid login first) → Dashboard → Submission Queue → filter by Status “Received” → open the anonymous reference you just created (show that Schedule Meeting is unavailable) → Change Status → Assign Staff → Add Resolution Note → open identified complaint SVP-4A72KD → Schedule Meeting → Meetings page → Analytics. Return to the student Track page to show the changes.
  5. Forms & validation. Use sections E–G: required vs optional, data types, formats, lengths, and anonymous vs identified data.
  6. Requirements. Close with the coverage table. Use “Reset demo data” in the page footer before presenting.
